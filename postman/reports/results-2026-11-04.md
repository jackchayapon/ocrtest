| 502 เดิมมี proxy connection-closed errors และสัมพันธ์เชิงเวลากับ process starts | CONFIRMED | 15:13:44/15:23:50 เกิด 502 ระยะเวลา 51,968/53,610 ms โดย upstreamErrors มี connection-closed indication แล้วมี process starts 15:13:50/15:23:57; ยังไม่ทราบเหตุที่ connection/process สิ้นสุด |

| Response ใหญ่เพิ่ม allocation pressure เมื่อรวม batches | LIKELY เป็นความเสี่ยงที่ควรวัด | single REC ~3.33 MB; ยังไม่วัด memory ภายใต้ concurrency จึงไม่ใช่ root cause ที่พิสูจน์แล้ว |

## Recommended next step

1. ส่ง historical Request IDs ในรายงาน investigation เดิมให้ CDGS ตรวจ error details และ worker/model load state
2. เตรียม isolated staging พร้อม resource limits/weights เทียบ production แล้วจึงรัน B ก่อน C จับ per-request memory/exit signals และ actual upstream concurrency
3. เสนอปรับ diagnostic allowlist: model params, batch count, participants, dimensions, safe upstream error code/details และจำแนก UPSTREAM_MODEL_ERROR ต่างจาก schema validation — ยังไม่ apply
4. ตรวจขนาด raw REC output/serialization ใน staging ก่อนพิจารณาเปลี่ยน response หรือ memory limits ไม่เพิ่ม retry422หรือเปลี่ยน weight เพื่อกลบอาการ

ไม่มีการแก้ production code/config/model records, restart/redeploy, commit/push หรือใช้ข้อมูลจริงเป็น test payload
